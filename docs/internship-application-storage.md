# Internship application storage

New applications use the existing MongoDB database (`akradhii`), not the Vercel filesystem. Configure `MONGODB_URI` with a reachable hosted MongoDB deployment and run `node --env-file=.env.local scripts/migrate-internship-applications.mjs` against each environment before accepting traffic. The script creates the application ID/status indexes and the rate-bucket TTL index; it does not delete or import existing data. Existing local `data/internship-applications.json` records are not automatically migrated: preserve any backup and plan a reviewed import separately.

`internshipApplications` stores an application ID, track and plan slugs and names, applicant fields, plan duration and amount, pending status, creation time, and consent acceptance time and version. `_id` is a hash of the required idempotency key; a repeated key and matching payload returns the original record, while reuse with different details returns 409. The browser keeps the key for retries with unchanged values during the current page session. It does not survive a page reload. The key and application details should not be logged.

## Integration tests

Run `npm run build`, then `npm run test:integration`. With no `MONGODB_TEST_URI`, the suite starts a disposable real MongoDB using the pinned `mongodb-memory-server` dev dependency; it may download a MongoDB binary on its first run. The suite creates a random database named `test_internship_<random>`, runs the actual migration against it, starts separate local Next servers and drops only that database afterwards. No transactions are used, so a standalone MongoDB process suffices. Unit tests remain available via `node --test tests/*.test.mjs`.

To test on an **isolated staging Atlas cluster**, set `MONGODB_TEST_URI` to a staging-only credential with permission to create and drop test databases, then run the same commands. For example in PowerShell: `$env:MONGODB_TEST_URI = '<staging-only URI>'`, then `npm run test:integration`. The suite never reads or inherits the parent `MONGODB_URI`; it generates the database name itself, enforces the `test_` prefix, and passes the test URI and name explicitly to the migration and local Next servers. It does not migrate the staging application's database. Use a credential restricted to an isolated test cluster: a random prefix is not a substitute for access controls. Do not place production credentials in `MONGODB_TEST_URI`.

The HTTP verify test exercises the production-mode fail-closed endpoint, which currently returns a generic 503 for all lookups because no production certificate registry exists. It does not prove nonproduction valid/invalid lookup semantics or the behaviour of a future registry.

`internshipApplicationRateLimits` is a shared fixed-window counter (eight apply or contact requests, or 30 verify requests per IP per ten minutes, with independent scopes). The atomic MongoDB update is shared by serverless instances; TTL is for cleanup, not enforcement. The `expiresAt` value is written as a BSON Date, not a string. A fixed window allows bursts on either side of a boundary. Missing database access or missing client IP in production fails closed for all three endpoints.

On Vercel (`VERCEL=1`), the helper uses only a single valid IP in `x-forwarded-for`. [Vercel documents](https://vercel.com/docs/headers/request-headers#x-forwarded-for) that it overwrites this header to prevent spoofing, and notes that an Enterprise trusted-proxy configuration can change the trust boundary. Do not expose the app directly behind a different proxy with this assumption; non-Vercel production fails closed. Development uses a shared loopback identity and does not trust incoming forwarding headers. Test the real staging proxy chain and missing-header behaviour before launch; those cannot be confirmed from source alone. Vercel/Atlas network access must also be verified in staging. The MongoDB client is cached in module-level variables in `src/lib/db/mongodb.ts` per warm instance; separate serverless instances still use separate connections.

Certificate verification is disabled in production because its only repository is demo data. In nonproduction, malformed, missing, unknown and rate-limited IDs return the same generic 404; successful lookups necessarily distinguish valid IDs. No submitted ID is logged by the route. No request bodies are logged in the apply, contact or verify handlers. The local `data` directory currently contains only `.gitkeep`; other machines, backups and deployed environments have not been inspected for legacy application records.
